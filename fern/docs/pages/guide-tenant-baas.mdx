# Tenant BaaS — Sub-Client Account Creation

Tenants operating as Banking-as-a-Service (BaaS) integrators can programmatically create accounts for their end-users. The flow has three steps:

1. Create a client identity — `POST /api/v1/clients`
2. Open a payment account for that client — `POST /api/v1/accounts`
3. Activate the account — `POST /api/v1/accounts/{id}/activate`

All endpoints accept either a **Bearer JWT** (`Authorization: Bearer <token>`) or direct **API Key** authentication (`x-key-id` + `x-secret-key` headers).

The ownership link is established automatically: the `client_id` from your authentication token becomes the `parent_client_id` of every sub-client you create. You can later act on accounts you own without any extra parameters.

---

## Step 1 — Create Client Identity

`POST /api/v1/clients` creates a new end-user identity in the platform. The account is created in **active** status immediately — no OTP or document verification is required in the programmatic BaaS flow.

**Required scope:** `clients:write`

```bash
curl -X POST https://api.brzip.com.br/api/v1/clients \
  -H "Authorization: Bearer <your-bearer-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "person_type": "individual",
    "name": "João Silva",
    "email": "joao@example.com",
    "password": "s3cur3P@ssword",
    "cpf": "12345678900",
    "phone": "+5511999999999"
  }'
```

For company accounts:

```bash
curl -X POST https://api.brzip.com.br/api/v1/clients \
  -H "Authorization: Bearer <your-bearer-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "person_type": "company",
    "name": "Acme Pagamentos Ltda",
    "email": "financeiro@acme.com.br",
    "password": "s3cur3P@ssword",
    "cnpj": "12345678000195",
    "company_name": "Acme Pagamentos Ltda",
    "trade_name": "Acme Pay",
    "phone": "+5511933334444"
  }'
```

**Request fields:**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `person_type` | string | Yes | `"individual"` or `"company"` |
| `name` | string | Yes | Full name or legal name |
| `email` | string | Yes | Must be unique across the platform |
| `password` | string | Yes | Minimum 8 characters |
| `cpf` | string | If `individual` | 11-digit CPF |
| `cnpj` | string | If `company` | 14-digit CNPJ |
| `company_name` | string | If `company` | Full legal company name |
| `trade_name` | string | No | Trade name / fantasy name |
| `phone` | string | No | International format, e.g. `+5511999999999` |

<Callout intent="info">
  You do not need to pass your `client_id` anywhere in this request. The platform derives it from your authentication token and automatically sets it as the sub-client's parent.
</Callout>

**Response (201):**

```json
{
  "success": true,
  "message": "client created",
  "data": {
    "client_id": "b7c4e902-1a2b-4f3d-9c8e-112233445566",
    "status": "active",
    "provisioning": {
      "wallet": true,
      "apiKey": true,
      "modules": true,
      "onboarding": true
    },
    "api_key": {
      "key_id": "key_abc123def456",
      "secret_key": "sec_xyz789ghi012"
    }
  }
}
```

<Callout intent="warning">
  Save the `api_key.key_id` and `api_key.secret_key` from the response. The secret key is shown **only once** at creation and cannot be retrieved later.
</Callout>

**Errors:**

| HTTP | Code | Meaning |
|------|------|---------|
| 400 | `MISSING_PERSON_TYPE` | `person_type` is absent or invalid |
| 400 | `WEAK_PASSWORD` | Password has fewer than 8 characters |
| 400 | `MISSING_CPF` | CPF required for `individual` but not provided |
| 400 | `MISSING_CNPJ` | CNPJ required for `company` but not provided |
| 400 | `MISSING_COMPANY_NAME` | `company_name` required for `company` |
| 409 | `EMAIL_EXISTS` | Email address is already registered |

## Step 2 — Create Payment Account

`POST /api/v1/accounts` opens a payment account for the sub-client created in Step 1.

**Required scope:** `accounts:write`

When you provide `client_id`, the identity fields (`person_type`, `document`, `name`, `email`) are **optional** — the platform fetches them automatically from the client record. Pass them explicitly only if you want to override.

```bash
curl -X POST https://api.brzip.com.br/api/v1/accounts \
  -H "Authorization: Bearer <your-bearer-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "b7c4e902-1a2b-4f3d-9c8e-112233445566"
  }'
```

The platform will look up the sub-client's CPF/CNPJ, name, and email and use them to open the account. If you pre-reserved an account number, include it:

```bash
curl -X POST https://api.brzip.com.br/api/v1/accounts \
  -H "Authorization: Bearer <your-bearer-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "b7c4e902-1a2b-4f3d-9c8e-112233445566",
    "account_number": "9876543",
    "reservation_id": "res_3fa85f64-5717-4562-b3fc-2c963f66afa6"
  }'
```

**Request fields:**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `client_id` | string (UUID) | No¹ | The sub-client's `client_id` from Step 1. If omitted, creates an account for your own credentials |
| `account_number` | string | No | Pre-reserved account number (from `/accounts/reserve`) |
| `reservation_id` | string | If `account_number` set | Possession key returned by `/accounts/reserve` |
| `account_type` | string | No | `"personal"` (default) or `"business"` |
| `person_type` | string | No¹ | Auto-filled from client record when `client_id` is provided |
| `document` | string | No¹ | CPF or CNPJ — auto-filled when `client_id` is provided |
| `name` | string | No¹ | Auto-filled when `client_id` is provided |
| `email` | string | No¹ | Auto-filled when `client_id` is provided |
| `phone` | string | No | Contact phone |

¹ Required when `client_id` is not provided.

**Response (201):**

```json
{
  "success": true,
  "data": {
    "id": "a612b202-6690-4d24-ba35-2e36c8f3c0ce",
    "client_id": "b7c4e902-1a2b-4f3d-9c8e-112233445566",
    "account_number": "9876543",
    "branch_code": "0001",
    "account_type": "personal",
    "state": "pending",
    "kyc_level": 0,
    "person_type": "individual",
    "document": "12345678900",
    "name": "João Silva",
    "email": "joao@example.com",
    "created_at": "2026-07-26T14:30:00Z",
    "updated_at": "2026-07-26T14:30:00Z"
  }
}
```

**Errors:**

| HTTP | Code | Meaning |
|------|------|---------|
| 400 | `MISSING_RESERVATION_ID` | `account_number` was provided but `reservation_id` was not |
| 404 | `CLIENT_NOT_FOUND` | `client_id` does not exist or does not belong to you |
| 409 | `DOCUMENT_IN_USE` | CPF/CNPJ already has an account in the platform |
| 403 | `RESERVATION_INVALID` | `reservation_id` is invalid, expired, or does not match the `account_number` |

## Step 3 — Activate the Account

`POST /api/v1/accounts/{id}/activate` transitions the account from `pending` to `active`. After activation, the account can receive and send PIX and boleto.

**Required scope:** `accounts:activate`

```bash
curl -X POST https://api.brzip.com.br/api/v1/accounts/a612b202-6690-4d24-ba35-2e36c8f3c0ce/activate \
  -H "Authorization: Bearer <your-bearer-token>"
```

No request body is required.

**Response (200):**

```json
{
  "account_id": "a612b202-6690-4d24-ba35-2e36c8f3c0ce",
  "status": "active"
}
```

After activation, a `account.activated` webhook event is fired to your configured webhook endpoint.

**Errors:**

| HTTP | Code | Meaning |
|------|------|---------|
| 404 | `ACCOUNT_NOT_FOUND` | Account does not exist or does not belong to you |
| 409 | `INVALID_STATE_TRANSITION` | Account is not in a state that allows activation |

## (Optional) Pre-Reserve an Account Number

If you need to assign a specific account number before creating the account, use the reserve endpoint:

**Required scope:** `accounts:reserve`

```bash
curl -X POST https://api.brzip.com.br/api/v1/accounts/reserve \
  -H "Authorization: Bearer <your-bearer-token>" \
  -H "Content-Type: application/json" \
  -d '{
    "reference_id": "onb_my-idempotency-key-for-this-client"
  }'
```

**Request fields:**

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `account_number` | string | No | Specific number to reserve — omit for auto-assignment |
| `reference_id` | string | Recommended | Idempotency key; if omitted a random UUID is generated per call |
| `account_type` | string | No | `"PF"` for individual, `"PJ"` for company |

**Response (201):**

```json
{
  "account_number": "9876543",
  "reservation_id": "res_3fa85f64-5717-4562-b3fc-2c963f66afa6",
  "branch_code": "0001",
  "reference_id": "onb_my-idempotency-key-for-this-client"
}
```

<Callout intent="warning">
  The `reservation_id` is returned **once** and is the possession key needed in Step 2. Store it alongside the `account_number`.
</Callout>

**Errors:**

| HTTP | Code | Meaning |
|------|------|---------|
| 409 | `ACCOUNT_NUMBER_UNAVAILABLE` | Requested `account_number` is already in use or reserved |

## Checking Account Status

`GET /api/v1/accounts/{id}` returns the current state and metadata of an account. You can query accounts belonging to your sub-clients.

**Required scope:** `accounts:read`

```bash
curl https://api.brzip.com.br/api/v1/accounts/a612b202-6690-4d24-ba35-2e36c8f3c0ce \
  -H "Authorization: Bearer <your-bearer-token>"
```

**Response (200):**

```json
{
  "id": "a612b202-6690-4d24-ba35-2e36c8f3c0ce",
  "account_number": "9876543",
  "branch_code": "0001",
  "account_type": "personal",
  "state": "active",
  "kyc_level": 0,
  "created_at": "2026-07-26T14:30:00Z",
  "updated_at": "2026-07-26T14:30:01Z",
  "activated_at": "2026-07-26T14:30:01Z"
}
```

**Account states:**

| State | Description |
|-------|-------------|
| `pending` | Account created, not yet activated |
| `active` | Fully operational |
| `suspended` | Temporarily restricted |
| `blocked` | All operations halted |
| `closed` | Terminal — cannot be reopened |

## Transacting on Behalf of a Sub-Client

To perform PIX or balance operations as a sub-client, use one of two approaches:

### Option A — assume-client token (recommended)

Exchange your API key credentials for a scoped Bearer Token that acts as the sub-client. Requires `auth:assume-client` scope on your API key.

```bash
curl -X POST https://api.brzip.com.br/api/v1/auth/assume-client \
  -H "x-key-id: <your-key-id>" \
  -H "x-secret-key: <your-secret-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "client_id": "b7c4e902-1a2b-4f3d-9c8e-112233445566",
    "scopes": ["pix:cashout:write", "pix:balance:read"],
    "expires_in": 900
  }'
```

**Response (201):**

```json
{
  "token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 900,
  "expires_at": "2026-07-26T15:30:00Z",
  "scopes": ["pix:cashout:write", "pix:balance:read"],
  "assumed_client_id": "b7c4e902-1a2b-4f3d-9c8e-112233445566"
}
```

Use the `token` directly in subsequent calls — no extra headers needed:

```bash
curl -X POST https://api.brzip.com.br/api/v1/pix/cash-out \
  -H "Authorization: Bearer <assumed-token>" \
  -H "X-Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{"amount": 5000, "pix_key": "destinatario@email.com"}'
```

| Field | Notes |
|-------|-------|
| `scopes` | Cannot exceed your own API key's scopes |
| `expires_in` | Max 3600 seconds (1 hour), default 900 (15 min) |

### Option B — Sub-client's own Bearer Token

Use the `api_key` returned in Step 1 to generate a Bearer Token for the sub-client directly:

```bash
curl -X POST https://api.brzip.com.br/api/v1/auth/bearer-token \
  -H "x-key-id: <sub-client-key-id>" \
  -H "x-secret-key: <sub-client-secret-key>" \
  -H "Content-Type: application/json" \
  -d '{"scopes": ["pix:cashout:write", "pix:balance:read"]}'
```

The returned `token` is a Bearer Token authenticated as the sub-client. Use it in the `Authorization` header for PIX operations.

## Complete Flow

```
1. POST /api/v1/clients
   Body: { person_type, name, email, password, cpf/cnpj }
   → Returns: client_id, api_key.key_id, api_key.secret_key

2. POST /api/v1/accounts
   Body: { client_id }
   → Returns: account.id, account_number, branch_code, state: "pending"

3. POST /api/v1/accounts/{account.id}/activate
   → Returns: { account_id, status: "active" }
   → Fires: account.activated webhook

To transact as the sub-client:
   POST /api/v1/auth/assume-client  →  scoped Bearer Token
```
