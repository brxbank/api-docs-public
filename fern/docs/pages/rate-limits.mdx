# Rate Limits

The BRZ API enforces rate limits to ensure fair usage and system stability.

## Default Limits

Rate limiting uses a token-bucket algorithm applied per authenticated client (identified by the client ID resolved from your credentials; unauthenticated requests are keyed by source address).

| Metric | Limit |
|--------|-------|
| Sustained rate | 50 requests/second per client |
| Burst | Bucket capacity of 100 requests |

## Exceeding the Limit

When you exceed the rate limit, the API returns:

- **HTTP Status**: `429 Too Many Requests`
- **Header**: `Retry-After` — the number of seconds to wait before retrying

### Example Response

```json
{
  "error": "rate_limit_exceeded",
  "message": "Too many requests. Please retry after the Retry-After period."
}
```

<Note>
The `Retry-After` header on a general rate-limit `429` is currently a fixed `1` (second). DICT PIX-key lookups are governed by a separate BACEN-mandated limiter that returns its own `429` with a longer `Retry-After`. Always honor the `Retry-After` header value rather than assuming a fixed delay.
</Note>

## Best Practices

1. **Implement exponential backoff**: When receiving a 429 response, wait for the duration specified in the `Retry-After` header before retrying.
2. **Use idempotency keys**: Include the `X-Idempotency-Key` header in POST requests to safely retry without creating duplicate operations.
3. **Batch operations**: Where possible, batch multiple operations into fewer API calls.
4. **Cache responses**: Cache responses for read operations (e.g., balance checks, key lookups) to reduce unnecessary API calls.
5. **Monitor usage**: Track your API usage patterns to stay within limits.

## Requesting Higher Limits

If your use case requires higher rate limits, contact the BRZ support team to discuss custom limits for your account.
